# تكليفات فريق الـAgents — Agentic ERP

**نسخة جاهزة للتوزيع على فريق من خمسة أشخاص**

**الحالة:** مواصفات تنفيذ للمرحلة التالية؛ الـAgents وواجهة التطبيق لم يتم تنفيذهم بعد.

**الأساس الحالي:** PostgreSQL وSQLAlchemy وAlembic وDocker وبيانات مصححة ومتحقق منها. راجع دليل التصميم التقني قبل تغيير قاعدة البيانات.

## 1. الرسالة المشتركة التي ترسلها للفريق

> هنطوّر خمسة مكونات مترابطة: Orchestrator، Sales Agent، Inventory Agent، Procurement Agent، وReturns Agent. كلهم يشتغلوا في تطبيق Python واحد وبنفس عقود الرسائل والأدوات. المطلوب من كل Agent قراءة بيانات ERP المسموح بها، وتحويل طلب محدد إلى حقائق موثقة وتوصية واضحة. الـOrchestrator وحده يوزع المهام ويجمع النتائج. ممنوع أي Agent يتصل بقاعدة البيانات مباشرة أو يكتب في جداول العمليات أو ينادي Agent آخر مباشرة. أي تغيير فعلي في ERP يمر من كود حتمي يتحقق من القرار الموجود في ملف موافقة المدير، ثم ينفذ معاملة قاعدة بيانات واحدة ويسجل الأثر.

## 2. قواعد ثابتة على الخمسة

1. **نفس التقنية:** Python 3.12، PostgreSQL الحالي، SQLAlchemy الموجود، Pydantic لعقود الإدخال والإخراج، وDocker للتشغيل المحلي. FastAPI يكون طبقة HTTP مشتركة عندما يبدأ تطوير API.
2. **لا تختاروا خمسة أطر Agents مختلفة.** ابدأوا بوحدات Python عادية خلف واجهة Agent مشتركة. اختاروا مزود نموذج واحدًا أو واجهة مزود محايدة للفريق كله؛ لا يضع كل مطور تكاملاً مختلفاً.
3. **الاتصال بين الـAgents عبر Orchestrator فقط.** Sales لا يطلب من Inventory مباشرة. يرسل Sales طلب بياناته للـOrchestrator، والـOrchestrator يوزع مهمة Inventory، ثم يمرر النتيجة.
4. **القراءة عبر أدوات محددة فقط.** ممنوع اتصال SQL مباشر من كود الـAgent أو SQL حر أو استدعاء ملفات/شبكة/أوامر نظام من النموذج.
5. **لا كتابة تشغيلية من الـAgents.** لا إنشاء Order أو PO أو Refund أو Stock Movement أو تغيير كمية المخزون. الوكيل يقترح فقط.
6. **الموافقة بملف المدير.** المدير يغير حقول القرار والملاحظة فقط: Approved، Rejected/Cancelled، أو Needs changes. أي تغيير في أصناف الطلب أو كمياته يصير Revision جديداً ويحتاج مراجعة جديدة.
7. **الكود الحتمي يحسب ويقرر القواعد الدقيقة.** الأسعار والضرائب والإجماليات والحجز وحالات المعاملات لا تعتمد على تخمين النموذج.
8. كل نتيجة تفرق بوضوح بين **معلومة من قاعدة البيانات** و**استنتاج أو توصية**، وتذكر مراجع السجلات التي استندت إليها.
9. الفرع والمخزن والتاريخ جزء من نطاق الطلب. لا تجمعوا مخازن الفروع في رقم واحد من غير إظهار نطاق كل مخزن.
10. لا تستخدموا أي بيانات حقيقية أثناء التطوير؛ الداتا الحالية Synthetic للاختبار.

### ما تم إنجازه وما لم يتم

- المنفذ والمتحقق: قاعدة البيانات الأساسية، الميجريشنز، الاستيراد، Docker، 45 فحص مصالحة و11 اختباراً.
- المطلوب منكم: طبقة الأدوات، الـOrchestrator، الـAgents، ملفات المراجعة والموافقة، خدمات الكتابة الحتمية واختبارات التكامل.
- قاعدة Phase 1 الحالية فيها جداول بيانات Synthetic باسم users/roles/permissions، لكنها **ليست** نظام دخول. لا تستخدموها لتسجيل الدخول أو لتحديد من وافق. لا يوجد في MVP حسابات مستخدمين أو تسجيل دخول.

## 3. العقد الذي يجب الاتفاق عليه قبل تقسيم الكود

يبدأ الفريق بتثبيت نموذجين مشتركين في مجلد مشترك. لا يبدأ كل شخص بكتابة شكل رسالة منفصل.

### 3.1 TaskEnvelope — رسالة المهمة إلى Agent

الحقول المطلوبة:

| الحقل | الغرض |
|---|---|
| run_id | يربط كل المهام بتنفيذ واحد للطلب أو التقرير. |
| task_id | معرف فريد لهذه المهمة. |
| parent_task_id | المهمة السابقة التي نتجت عنها هذه المهمة، إن وجدت. |
| task_type | نوع محدود مثل inventory.availability أو sales.summary. |
| branch_id | الفرع المطلوب؛ يكون مطلوباً في المهام التشغيلية، وقد يكون فارغاً فقط لتقرير مصرح به عن كل الفروع. |
| warehouse_id | المخزن المطلوب إذا كانت المهمة تخص مخزناً محدداً. |
| input_refs | معرفات الطلب/المراجعة أو سجلات ERP المطلوبة بدلاً من نسخ ملفات كبيرة داخل الرسالة. |
| parameters | فلاتر محددة مثل SKU والفترة الزمنية والكمية المطلوبة. |
| allowed_tools | قائمة أسماء الأدوات المتاحة لهذا النوع من المهام. |
| attempt وdeadline_seconds | حد المحاولات والوقت. |

يجب أن يكون نوع المهمة محدوداً ومتحققاً منه. لا تضعوا SQL أو كلمة سر أو DATABASE_URL في الرسالة.

### 3.2 AgentResult — نتيجة موحدة من Agent

الحقول المطلوبة:

| الحقل | الغرض |
|---|---|
| run_id وtask_id وagent_name | ربط النتيجة بالمهمة والوكيل الصحيح. |
| status | واحدة من succeeded، no_data، needs_input، failed، timed_out. |
| facts | حقائق منظمة حصل عليها الوكيل من الأدوات. |
| source_refs | مراجع المصدر، مثل اسم الجدول ومفتاح السجل؛ لا تكتفوا بجملة عامة. |
| recommendation | اقتراح اختياري واضح، لا يُعامل على أنه حقيقة أو موافقة. |
| assumptions وwarnings | افتراضات وتحذيرات مثل نقص مخزون أو غياب سياسة مرتجعات. |
| error | رمز وخطأ مختصر قابل للعرض، بدون Stack Trace أو أسرار. |

كل الرسائل تُعرّف بـPydantic وتُراجع باختبارات. احفظوا الاستنتاج النهائي المختصر ومراجع الأدلة؛ لا تحفظوا Chain of Thought أو أسرار النموذج.

### 3.3 واجهة Agent مشتركة

كل Agent يلتزم بالواجهة المنطقية التالية:

~~~python
class Agent:
    name: str
    supported_task_types: set[str]

    def run(self, task: TaskEnvelope, tools: ReadOnlyTools) -> AgentResult:
        ...
~~~

هذه واجهة تصميمية مقترحة وليست كوداً موجوداً بعد. لو احتاج Agent نموذجاً لغوياً، يطلب منه صياغة تحليل أو تفسيراً فقط؛ ثم يتحقق من الإخراج ويضيف الأدلة التي أعادتها الأدوات. النتيجة لا تصل مباشرة لخدمة الكتابة.

## 4. الشخص الأول — Orchestrator / منسق المهام

### الهدف

بناء منسق واحد يستقبل Trigger، يحول الطلب إلى TaskEnvelope أو أكثر، يوجه كل مهمة إلى Agent مناسب، ينتظر النتائج، يتحقق من شكلها، يجمعها، ويطلب إنشاء تقرير أو ملف مراجعة. الـOrchestrator هو مسار التنسيق، وليس قاعدة بيانات ولا صاحب قرار المدير.

### المطلوب تنفيذه

1. تعريف قاموس task_type والوكيل الذي يملكه؛ مثال:
   - sales.summary → Sales Agent
   - sales.order_draft → Sales + Inventory
   - inventory.availability → Inventory Agent
   - inventory.low_stock → Inventory ثم Procurement
   - procurement.replenishment_draft → Procurement Agent
   - returns.status_summary أو returns.review_draft → Returns Agent
2. تنفيذ دورة Run: إنشاء run، حفظ الحالة، إرسال المهام، جمع النتائج، وحفظ الملخص النهائي ومراجع المصادر.
3. السماح بالمهام المتوازية عندما تكون مستقلة، مثل Sales summary وInventory availability. في Low Stock، انتظر قائمة المنتجات من Inventory ثم كلف Procurement بتحليل تلك المنتجات.
4. التحقق من أن كل نتيجة تخص task_id وrun_id الصحيحين وأنها تطابق AgentResult.
5. إدارة الأخطاء: timeout، no_data، إخراج غير صالح، فشل أداة، فشل Agent. أظهر Partial Result فقط إذا كانت البيانات المتبقية مفيدة وواضحة؛ وإلا أوقف السلسلة ولا تخترع نتيجة.
6. منع تكرار التنفيذ عند إعادة وصول نفس Trigger، باستخدام Idempotency Key للطلب.
7. تمرير النتائج إلى Workbook Service لإنشاء ملف مراجعة. لا تستدعِ خدمة كتابة ERP بنفسك.
8. حفظ سجل التشغيل والمهام والحالة والوقت والأخطاء المختصرة في جداول workflow المقترحة، بعد إضافة ميجريشن.

### وظائف مقترحة

- ingest_trigger()
- validate_request()
- classify_intent()
- plan_tasks()
- dispatch_task()
- collect_results()
- validate_agent_result()
- merge_results()
- handle_timeout_or_failure()
- create_review_file()

### ممنوعات

- لا يكتب في جداول Sales/Inventory/PO/Refund.
- لا يعطي Agent نطاق فروع أوسع من طلبه.
- لا يمرر كلام المستخدم أو خلية Excel إلى النموذج على أنها تعليمات نظام.
- لا يسمح للـAgents بالتخاطب المباشر.
- لا يستخدم LLM لتحديد الضرائب أو قبول الموافقة أو تقرير أن المخزون حُجز فعلياً.

### التسليم والاختبارات

- Orchestrator يعمل بـFake Agents قبل دمج أي مزود نموذج.
- اختبارات: مهمة واحدة، مهمتان بالتوازي، سلسلة Inventory ثم Procurement، وكيل يرجع no_data، timeout، نتيجة غير مطابقة، إعادة Trigger بنفس المفتاح، وفشل وكيل ينتج Partial Result موضحاً.
- مخطط بسيط يبين كل task_type والـAgent المسؤول ومتى يكون الاستدعاء متوازياً أو متتابعاً.

## 5. الشخص الثاني — Sales Agent

### الهدف

تحليل أسئلة المبيعات وتجهيز مسودة طلب بيع من معلومات موثقة. هذا الوكيل لا يُصدر الطلب ولا يغير السعر ولا يؤكد توفر المخزون.

### المدخلات

- رقم الفرع المطلوب، وتاريخ أو فترة التقرير.
- نوع المهمة: ملخص مبيعات، تفسير حالة Order، أو تجهيز مسودة طلب.
- في طلب جديد: كود العميل، SKU، الكمية، القناة، والمخزن المطلوب إن حدده مقدم الطلب.
- معرفات الطلب/المراجعة ومراجع السجلات عند الاستعلام عن Order موجود.

### أدوات القراءة المسموحة

- get_sales_summary(branch_id, date_from, date_to, product_ids)
- get_product_catalog(sku_or_category, limit)
- get_customer_summary(customer_code)
- get_order_status(order_number)
- get_branch_warehouse_map(branch_id, as_of)

إذا لم تكن إحدى الأدوات موجودة، اكتب Interface وMock واكتب طلبها في عقد الفريق؛ لا تفتح اتصال قاعدة البيانات من Agentك.

### الوظائف التي يبنيها

- summarize_sales(): ملخص كميات وإيرادات للفترة والفرع المطلوبين، مع ذكر الفترة والفرع.
- draft_order_lines(): يطابق SKU بالكتالوج، يعيد خطوطاً مقترحة ويشير إلى العناصر غير المعروفة أو الكمية غير الصالحة.
- explain_order_status(): يشرح الحالة الحالية من بيانات ERP ومراجعها، ولا يعد العميل بموعد غير موجود في البيانات.
- validate_sales_result(): يتحقق أن كل منتج ورقم عميل له مرجع صحيح قبل إرجاع النتيجة.

### قواعد المبيعات

- السعر من قائمة المنتجات أو سياسة سعر حتمية يحددها الفريق لاحقاً. لا يخترع Agent خصماً أو سعراً.
- الإجمالي والضريبة والتقريب يحسبها Deterministic Sales Service باستخدام Decimal، وليس نص النموذج.
- Agent يطلب من Orchestrator فحص المخزون؛ لا ينادي Inventory بنفسه ولا يقول إن الطلب Reserved قبل كتابة الحجز في قاعدة البيانات.
- إذا لم يذكر الطلب فرعاً أو كان العميل/SKU غير معروف، يرجع needs_input أو تحذيراً واضحاً ولا يخمن.
- في حالة اختلاف بين الملف والكتالوج، أظهر القيمتين واطلب مراجعة.

### التسليم والاختبارات

- Sales Agent Module يلتزم بالعقد الموحد.
- اختبارات لملخص فترة، SKU غير موجود، عميل غير موجود، فرع محدد، كميات صحيحة/غير صحيحة، وسعر ثابت من مصدر البيانات.
- كل رقم في النتيجة إما مصدره أداة أو موسوم بأنه اقتراح، ولا يوجد إنشاء طلب حقيقي من Agent.

## 6. الشخص الثالث — Inventory Agent

### الهدف

تقديم صورة صحيحة عن المخزون حسب الفرع والمخزن والمنتج، وتحليل توفر المنتجات أو مخاطر النقص. لا يغير هذا الوكيل الكميات ولا ينشئ Reservation حقيقياً.

### المدخلات

- الفرع، المخزن أو قاعدة اختيار مخزن واضحة، التاريخ/وقت اللقطة، وSKU أو قائمة المنتجات.
- في مهمة طلب بيع: كميات كل سطر المطلوبة.
- في فحص نقص: مجموعة الفروع/المخازن والفترة أو تكرار الفحص.

### أدوات القراءة المسموحة

- get_inventory_snapshot(branch_id, warehouse_id, product_ids, as_of)
- get_branch_warehouse_map(branch_id, as_of)
- get_stock_movement_history(warehouse_id, product_id, date_from, date_to)
- get_product_catalog(sku_or_category, limit)

### الوظائف التي يبنيها

- get_availability(): يرجع on_hand، reserved، available = on_hand - reserved، reorder_point، وتاريخ اللقطة لكل زوج مخزن/منتج.
- calculate_reservation_plan(): يحاكي هل يمكن توفير كامل خطوط الطلب من المخزن المختار. نتيجة محاكاة فقط؛ لا ينشئ أو يعدل Inventory Reservation.
- find_alternative_warehouses(): يقترح مخازن أخرى تخدم الفرع فعلياً في التاريخ المطلوب، ويعرض كميتها كل مخزن لوحده.
- analyze_low_stock(): يرتب النواقص حسب فرق المتاح عن نقطة إعادة الطلب، مع الأدلة.
- explain_stock_history(): يلخص حركات المخزون ضمن فترة محددة ويذكر نوع الحركة والمصدر.

### قواعد المخزون

- استخدم العلاقة الفعالة في branch_warehouse_services، ولا تعتبر كل Warehouse متاحاً لكل Branch.
- لا تجمع Central وRegional Warehouse في رصيد واحد دون التفصيل.
- لا تعتبر الكمية المحجوزة متاحة.
- لا تخصم الطلب من on_hand بمجرد الموافقة؛ الحجز يرفع reserved، وخروج البضاعة الفعلي يسجل حركة sale ويحدث on_hand لاحقاً.
- عند غياب سجل inventory لا تفترض صفر أو رقم موجود في سياق المحادثة؛ ارجع no_data/تحذيراً، ويقرر Orchestrator ما إذا كان الملف يحتاج مراجعة.
- إعادة فحص الكمية النهائية عند تنفيذ المعاملة مسؤولية Inventory/Sales Transaction Service الحتمي، مع قفل الصفوف؛ ليست مسؤولية Agent.

### التسليم والاختبارات

- اختبارات لكل الفروع الستة والمخازن الثلاثة وعلاقات الخدمة، زوج مخزن/منتج غير موجود، كمية محجوزة، رصيد أقل من المطلوب، وتغير البيانات بعد أخذ اللقطة.
- تأكد أن كل نتيجة تذكر as_of ونطاق المخزن وأن الدالة لا تملك أي write tool.

## 7. الشخص الرابع — Procurement Agent

### الهدف

تحليل خيارات إعادة التوريد وتجهيز اقتراح شراء للمراجعة. لا ينشئ Purchase Order ولا يتواصل مع الموردين.

### المدخلات

- منتجات مرشحة من Inventory Agent أو مهمة فحص مشتريات مستقلة.
- المخزن المقصود والكمية أو نطاق الطلب والتاريخ المتوقع.
- نتائج المخزون ونقطة إعادة الطلب، أو references لها؛ لا يثق في أرقام غير مرتبطة بمصدر.

### أدوات القراءة المسموحة

- get_supplier_options(product_ids, warehouse_id)
- get_open_purchase_orders(warehouse_id, product_ids)
- get_inventory_snapshot(branch_id, warehouse_id, product_ids, as_of)
- get_supplier_product_terms(supplier_id, product_ids, as_of)

### الوظائف التي يبنيها

- find_replenishment_candidates(): يستقبل نواقص موثقة ويستبعد المنتجات التي لديها كمية قيد الوصول إذا كان موعدها معروفاً.
- compare_suppliers(): يقارن الموردين الفعالين حسب تكلفة المورد ومدة التوريد والحد الأدنى للطلب والتفضيل المسجل، ويعرض أسباب الترتيب.
- draft_purchase_request(): ينشئ مقترحاً فقط: المورد المقترح، المنتج، الكمية، المخزن، التكلفة المتوقعة، lead time، الافتراضات.
- explain_purchase_option(): يشرح الاختيار ويعرض بدائل عند توفرها.

### قواعد الشراء

- لا يعتبر Purchase Order المفتوح مستلماً للمخزون. افصل المتاح فعلياً عن المتوقع وصوله.
- راعِ صلاحية supplier_products وتاريخها وMOQ وlead time من البيانات.
- لا تختلق ضريبة أو شحن أو مهلة غير موجودة.
- لا يرسل بريد/طلب شراء ولا ينشئ PO. الملف يعرض مقترحاً للمدير؛ بعد الموافقة ينشئ PO deterministic service.
- لا توجد حالياً دورة فواتير موردين ومدفوعاتهم مكتملة؛ لا تقدم أرصدة Accounts Payable كأنها حقيقة.

### التسليم والاختبارات

- سيناريوهات: مورد مفضل صالح، المورد غير صالح في التاريخ، MOQ أعلى من الحاجة، PO مفتوح يغطي بعض الحاجة، لا يوجد مورد، وفرع/مخزن غير مخدوم.
- اختبر أن توصية الشراء لا تغير purchase_orders أو inventory.

## 8. الشخص الخامس — Returns Agent

### الهدف

شرح حالة Return وPayment/Refund من السجلات، وتجهيز ملخص مراجعة للمدير. لا يوافق على المرتجع ولا يصدر Refund.

### المدخلات

- رقم Return أو Order أو Payment مع سبب الاستعلام.
- نطاق الفرع/العميل إذا احتاجته أداة القراءة.
- تفاصيل الأصناف والكمية والحالة أو disposition إذا كانت مسجلة.

### أدوات القراءة المسموحة

- get_return_and_refund_status(return_number)
- get_order_status(order_number)
- get_payment_summary(order_number)
- get_return_items(return_number)
- get_inventory_snapshot(branch_id, warehouse_id, product_ids, as_of)

### الوظائف التي يبنيها

- summarize_return(): يلخص الحالة والتاريخ والأصناف والكميات والسبب المسجل.
- check_refund_status(): يشرح refund المسجل وحالة payment ويربطهما بمراجع الصفوف؛ لا يقول إن الأموال وصلت للبنك من مجرد وجود سجل.
- draft_return_review(): يحضر بيانات للمراجعة مثل المنتج والكمية والحالة/disposition المقترحين إذا طلب ذلك، ويعرض ما ينقص.
- detect_return_data_issue(): يلفت النظر إلى كمية تتجاوز ما تم بيعه أو تعارض في ربط المنتج/الطلب حسب البيانات والقواعد الثابتة.

### قواعد المرتجعات

- لا توجد في المشروع سياسة مكتملة لأهلية الإرجاع أو مهلة الأيام أو قواعد الاستثناء. لا يخترع Agent هذه السياسة؛ اذكر أن القرار يحتاج قاعدة عمل وموافقة بشرية.
- لا يغير حالة returns ولا return_items ولا payment_refunds.
- تسجيل Refund تاريخي لا يعني تكامل دفع حي أو أن أموالاً أُرسلت. لا تنفذ أي تكامل دفع.
- إعادة المنتج للمخزون تعتمد على فحص الاستلام والحالة وقرار disposition؛ لا ترفع المخزون تلقائياً بسبب توصية Agent.

### التسليم والاختبارات

- اختبارات حالة requested/approved/received/rejected/refunded، Payment بانتظار/مكتمل/فاشل، مبلغ refund ضمن حد الدفعة، Return غير موجود، وسياسة غير محددة.
- كل نتيجة تفصل بين “الحالة المسجلة” و“التوصية”، ولا تستنتج اكتمال الدفع من نص غير موثق.

## 9. الأدوات المشتركة — مسؤولية مشتركة، لا يكتبها كل شخص بطريقته

تُعرّف الأدوات كواجهات مشتركة، ثم يملك شخص واحد تنفيذ كل أداة داخل Database Tool Gateway. جميع الـAgents تستخدم نفس النسخة:

| الأداة | البيانات التي ترجعها |
|---|---|
| get_branch_warehouse_map | مخازن الفرع التي تخدمه فعلياً في التاريخ المطلوب، وقدرات fulfillment/transfer. |
| get_product_catalog | SKU والاسم والفئة والسعر/التكلفة ونقطة/كمية إعادة الطلب للمنتجات المطابقة. لا يرجع كلمات مرور أو حقول غير لازمة. |
| get_customer_summary | وجود العميل وحالته والحد الأدنى من معلوماته اللازمة لمراجعة الطلب. |
| get_sales_summary | عدد الوحدات والإيراد والاتجاه حسب الفرع/المخزن/الفترة/المنتج، مع مرجع الاستعلام ومجال التاريخ. |
| get_order_status | حالة الطلب والشحن والدفع والسطور ذات العلاقة. |
| get_inventory_snapshot | on_hand وreserved وavailable ونقطة إعادة الطلب ووقت اللقطة لكل مخزن/منتج. |
| get_stock_movement_history | حركات المخزون الموثقة حسب المخزن والمنتج والفترة. |
| get_open_purchase_orders | كميات PO غير المستلمة والمتوقع وصولها إذا توفر التاريخ. لا تخلطها بالمخزون الحالي. |
| get_supplier_options | الموردون الفعالون وأسعار التوريد وMOQ وlead time وصلاحية العرض. |
| get_return_and_refund_status | الحالة والأصناف والدفعات والاستردادات المرتبطة بسجلات ERP. |

كل أداة يجب أن تستخدم SQL parameter binding، حدوداً للصفوف/الفترة، ونطاقاً تنظيمياً. توثيق الأداة يحدد الحقول المطلوبة، صلاحية التاريخ، معنى القيمة، وسياسة no_data.

### من يستعمل قاعدة البيانات ومتى؟

1. Intake وOrchestrator يقرآن/يسجلان **بيانات التشغيل والمهمة** من خلال Repositories، مثل workflow request وagent run/task.
2. أثناء التحليل، Agent يطلب أداة أعمال؛ الأداة تنفذ SELECT محدوداً من PostgreSQL وترجع حقائق ومفاتيح المصدر. **هنا فقط** يحصل Agent على معلومات قاعدة البيانات؛ لا يرى كلمة سر أو اتصال DB.
3. عند إنشاء ملف المراجعة، Workbook Service يأخذ Snapshot موثقاً وحقولاً حتمية للعرض.
4. عند إعادة الملف، Approval Importer يسجل استلام الملف والتحقق من البيانات. هذا ليس إذناً للكتابة إلا إذا القرار صحيح وينطبق على نفس Revision.
5. بعد Approved فقط، Transaction Service يستخدم اتصال كتابة محدوداً ومعاملة PostgreSQL؛ يعيد التحقق من الحالة والمخزون ويكتب السجلات ذات العلاقة كلها أو لا يكتب شيئاً.

~~~mermaid
sequenceDiagram
  participant Agent
  participant Orchestrator
  participant Tool as Read-only Tool Gateway
  participant DB as PostgreSQL
  participant Approval as Approval Importer
  participant Tx as Transaction Service
  Agent->>Orchestrator: طلب معلومات من مهمة محددة
  Orchestrator->>Tool: استدعاء اسم أداة مسموح + فلاتر نطاق
  Tool->>DB: SELECT parameterized ومحدد بالفرع/المخزن
  DB-->>Tool: صفوف/تجميعات مطلوبة فقط
  Tool-->>Orchestrator: حقائق + source_refs
  Orchestrator-->>Agent: نتيجة أداة محدودة للمهمة
  Agent-->>Orchestrator: AgentResult منظم
  Note over Agent,DB: لا يوجد اتصال Agent مباشر بقاعدة البيانات
  Approval->>Approval: فحص القرار والـRevision وHash المحتوى
  alt ملف موافقة صالح وApproved
    Approval->>Tx: أمر أعمال محدد + idempotency key
    Tx->>DB: معاملة كتابة محدودة + قيود + قفل المخزون
    DB-->>Tx: Commit أو Rollback
  else مرفوض أو قديم أو يحتاج تعديل
    Approval->>DB: سجل تدقيق للنتيجة فقط؛ لا أمر أعمال
  end
~~~

## 10. التنفيذ المشترك والتكامل

### أول اجتماع للفريق

قبل توزيع القصص، قرروا وسجلوا في README:

- أسماء task_type والـstatus النهائية.
- Pydantic schema واحد لـTaskEnvelope وAgentResult.
- قائمة الأدوات المشتركة وتواقيعها ومَن ينفذ كل Tool.
- ما يفعله كل نوع Trigger وما يخرجه.
- نموذج ملف request ونموذج ملف approval والأعمدة الوحيدة التي يسمح للمدير بتغييرها.
- طريقة تشغيل مزود النموذج (أو Stub في أول أسبوع) وحدود timeout/retry.
- قاعدة المخزون عند عدم كفاية كل الأصناف: MVP يقترح all-or-none، وأي تغيير في الكمية يحتاج Revision جديدة.

### مراحل التنفيذ

1. **تثبيت العقد:** شخص 1 يفتح Pull Request للعقود والـOrchestrator skeleton، والخمسة يراجعون. استخدموا Fake Agents وFake Tools في البداية.
2. **قاعدة القراءة:** نفذوا ReadOnly Tool Gateway واختبار Scope لكل فرع/مخزن. يجب ألا توجد credentials كتابة في عملية Agents.
3. **بناء الوكلاء بالتوازي:** الأشخاص 2–5 يكتبون Agent Module يلتزم بنفس الواجهة، مع fixture/mock للبيانات. لا تنتظر Agent اكتمال الآخر.
4. **التوصيل:** شخص 1 يضيف كل Agent في registry ويربط task_type بالـAgent؛ يمرر النتائج من Agent لآخر فقط عن طريق Orchestrator.
5. **ملف المراجعة:** الفريق يثبت صيغة البيانات. شخص 1 ينسق مع شخصي Sales/Inventory لإنتاج تفاصيل الطلب والرصيد، ومع صاحب Procurement/Returns لنماذجهم اللاحقة. عملية import والموافقة يجب أن تكون خدمة حتمية منفصلة عن النموذج.
6. **التكامل من البداية للنهاية:** شغلوا سيناريو واحداً: ملف Sales → تحقق → Sales + Inventory → مراجعة → قرار المدير → تحقق → DB أو رفض بلا تغيير.
7. **توسيع النطاق:** بعد نجاح السيناريو الأول، أضيفوا Procurement وReturns، ثم التقارير المجدولة، وبعد القياس قرروا هل تحتاجون Queue.

### شروط قبول أي Agent Pull Request

- يلتزم بعقد Pydantic الموحد ويصرح بأنواع المهام التي يدعمها.
- لا يحتوي على اتصال PostgreSQL أو SQL أو credential في ملف Agent.
- الأدوات التي يستعملها مسماة ومضافة لقائمة allow-list، وكلها للقراءة.
- كل fact في AgentResult له source_ref، وكل توصية معنونة كتوصية.
- يحدد سلوكه مع missing/ambiguous/stale input وtimeout وtool failure.
- عند تشغيل اختباره، يثبت أن أياً من جداول الأعمال لم يتغير.
- يحتوي على اختبارات نجاح وفشل وعدم بيانات، وسيناريو فرع/مخزن.
- يضيف مثال إدخال وإخراج صغيرين في README خاص بمكونه.
- لا يضع مفاتيح API أو بيانات مستخدم حقيقية في الكود أو Fixtures.

## 11. ملخص جاهز تقوله لكل شخص

- **للشخص الأول:** “أنت مسؤول الـOrchestrator. ابنِ TaskEnvelope وAgentResult والـRegistry والـRouting وسجل التشغيل. خلّي المهام تمر عبرك، وتعامل مع timeout وpartial results، واستخدم Fake Agents أولاً. لا تكتب عمليات ERP.”
- **للشخص الثاني:** “أنت مسؤول Sales Agent. نفّذ ملخصات المبيعات ومسودة الطلب وتفسير الحالة بأدوات القراءة المسموحة. لا تخترع سعر/خصم ولا تنشئ Order. ارجع حقائق ومراجع وتوصية منظمة.”
- **للشخص الثالث:** “أنت مسؤول Inventory Agent. نفّذ availability والحجز المحاكى ونقص المخزون والبحث عن مخزن بديل، دائماً حسب branch_warehouse_services. لا تعدل الرصيد أو تنشئ حجزاً فعلياً.”
- **للشخص الرابع:** “أنت مسؤول Procurement Agent. قارن الموردين وشروطهم والـPO المفتوحة وجهز اقتراح شراء موثقاً. لا تنشئ PO ولا تتواصل مع المورد ولا تدعي أن المتوقع وصوله أصبح مخزوناً.”
- **للشخص الخامس:** “أنت مسؤول Returns Agent. لخّص حالة الإرجاع والدفعة/refund وجهز ملف مراجعة، ووضح السياسات الناقصة. لا توافق على إرجاع ولا تنفذ refund ولا تعتبر السجل التاريخي تكاملاً مع بوابة دفع.”

## 12. الخلاصة التي تحكم النظام

**الـAgent يقرأ ويحلل ويقترح؛ الـOrchestrator ينسق؛ المدير يقرر بملف؛ والكود الحتمي وحده ينفذ كتابة معتمدة في PostgreSQL.**

هذه التعليمات تعطي كل شخص Agent يملكه، مع واجهة مشتركة تمنع اختلاف طرق التنفيذ. ابدأوا بعقد الرسائل والأدوات، ثم وزعوا Agents الأربعة المتخصصة بالتوازي، وادمجوهم بمنسق واحد.
